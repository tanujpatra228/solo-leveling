## 1. Six findings

### H1 — the fix I proposed for the bundle was wrong

Both the M2 and M3 plans said the same thing: if the bundle overshoots, move the 252-row strength
standards table to a chunk loaded after first paint.

I finally measured it. **`standards.data.ts` is 3,733 bytes gzipped** — under **2%** of the 194.9 KB
of JavaScript. Lazy-loading it would save nothing worth the complexity, and it would put an `await`
in front of rank computation for no reason.

I asserted that twice without measuring it. It was a guess dressed as a remedy, and the remedy does
not work.

### H2 — the 200 KB budget was borrowed from the wrong kind of app

Measured today, after M3:

| Asset | Gzipped |
|---|---|
| `index-*.js` | 194,867 B |
| `index-*.css` | 5,294 B |
| `workbox-window` | 2,250 B |
| **Total** | **202,411 B — 197.7 KiB, or 202.4 KB** |

M3 added 8,539 bytes. Against the "200 KB" I wrote in the M2 plan, that is *over* in decimal bytes
and *under* in binary ones — which is a sign the number was never precise enough to enforce.

The deeper problem is that the number came from public-website thinking, where every visitor pays
the download. **This is an installed, precached PWA with one user.** Workbox precaches the whole
shell on first run, so the bundle is paid once at install and once per deploy — never per session —
and offline operation is guaranteed by the precache no matter how big it is.

So the budget needs re-deriving from what it actually costs *you*: a few seconds on a gym connection
at install time, and the same again each time I ship. That is a real cost, worth keeping modest, but
it is not the cliff a 200 KB line implies. M4 replaces the invented number with a measured one and a
stated reason.

**What is confirmed clean:** `qrcode` and `jsqr` are dependencies for System Link in M6 and are
correctly tree-shaken out — neither appears in the bundle. `motion` is imported through
`LazyMotion` + `m` exactly as M2-D5 required. So there is no obvious dead weight; it is genuinely
React, the router, Dexie, Zod and app code.

### H3 — CPU is measurable from here, and the expensive path has never been measured

This has been the longest-standing unknown in the project: *"local wall-clock is not CPU time and
the local runtime does not report CPU."* It is no longer unknown, and it did not need the dashboard.

The Workers analytics live in GraphQL rather than REST, and `workersInvocationsAdaptive` returns CPU
quantiles directly. Pulled live today:

| Metric | Value |
|---|---|
| `cpuTimeP50` | **780 µs — 0.78 ms** |
| `cpuTimeP99` | **2,994 µs — 2.99 ms** |
| `wallTimeP50` | 1,471 µs |
| `wallTimeP99` | 3,387 µs |
| requests / errors | 4 / 0 |
| **subrequests** | **0** |

Against a 10 ms limit, P99 sits at **30%**. The design target in `infrastructure.md` is 3 ms, and
P99 is 2.99 ms — which looks like a bullseye and is not one.

**Read the subrequest count.** Zero subrequests means **not one of those four requests touched D1.**
They were the health check, the 401, and the 404 I used to verify the deploy. So this measures the
cheap paths only.

The path the 10 ms budget was actually written for — `/api/sync`, with a rate-limit upsert, a hunter
upsert, up to thirteen multi-row inserts and a select — **remains unmeasured.** The number above is
a floor, not a verdict.

### H4 — the Actions workflow needs a credential I cannot create

CI cannot use wrangler's OAuth token; it needs a `CLOUDFLARE_API_TOKEN` in GitHub secrets. The
Cloudflare MCP server cannot mint one — `/user/tokens/permission_groups` returns
`9109 Unauthorized`, so that OAuth grant does not cover token creation. Confirmed twice now.

This is the one hard blocker in M4, and it is thirty seconds of your time. Details in §3.

### H5 — the "one-time setup script" is now disaster recovery, not setup

The plan has always carried a setup script that creates the D1 database, generates VAPID keys, sets
secrets and writes ids into `wrangler.jsonc`. Every one of those except the VAPID keys is now
already done, through the API.

So the script's purpose has changed: it is what you would run to rebuild this on a fresh machine or
a new Cloudflare account, not what you run to get started. That is worth having and worth
**demoting** — it is no longer on the critical path, and writing it before the VAPID keys exist
(M8) would mean writing half of it twice.

### H6 — `pnpm run deploy` does not run the tests

```
build:  pnpm run typecheck && vite build
deploy: pnpm run build && wrangler deploy
```

`build` runs the typechecker but never `vitest`. So a deploy can ship with 467 tests red and say
nothing. It has not bitten yet because I have been running the suite by hand — which is exactly the
habit CI exists to replace.

This matters most *because* of the Actions workflow: a pipeline built on the current `deploy` script
would automate shipping broken code.

## 2. What M4 does

Five commits, four of which need nothing from you.

| # | Commit | Needs you? | What lands |
|---|---|---|---|
| 1 | Test the deploy path | No | H6 — `vitest` in the release path, and a `verify` script |
| 2 | Measure the sync path | No | H3 — real CPU for the expensive route, recorded |
| 3 | Attribute the bundle | No | H1, H2 — one-off analysis, budget re-derived and stated |
| 4 | The Actions workflow | **Token** | H4 — push to `main` ships, after tests pass |
| 5 | Correct the documentation | No | Every number above written down where it is looked up |

### Commit 1 — the release path runs the tests

A `verify` script that runs typecheck and the suite, with `deploy` depending on it. Cheap, and it is
the precondition for commit 4 being safe rather than dangerous.

Also worth adding here: a **post-deploy smoke check**. The deploy verification I ran by hand — health
answers, unauthenticated sync is 401, an unknown API path is a JSON 404, `/gate` returns the shell
through the SPA fallback — is four `curl` calls and belongs in a script, so the workflow can fail a
bad deploy instead of announcing a green tick over one.

### Commit 2 — measure the path that matters

The mechanism is proven; what is missing is traffic through the expensive route. The measurement is:

1. Mint a throwaway licence key locally, using the real `encodeLicenseKey`.
2. Push a realistic batch to the **deployed** Worker — a full Friday Legs session is 17 sets plus a
   session row, which is the shape of a genuine sync.
3. Pull it back, then push a second batch so the dedupe path is measured too.
4. Re-query the GraphQL quantiles, filtered to that window.
5. `POST /api/forget-me` with the throwaway key, so the synthetic hunter leaves nothing behind.

That last step is why this is safe to run against production: the mirror is tenant-scoped and
`forget-me` deletes the tenant outright.

**What the numbers decide.** If sync P99 lands near 3 ms, the 16-row insert chunking from M1's C3 is
comfortable and `infrastructure.md`'s design target stands. If it lands near 8 ms, the row cap wants
lowering before M6 turns sync on for real. Either way it stops being a guess, and M6 gets to start
from a measured number instead of inheriting mine.

### Commit 3 — attribute the bundle, then decide the budget

Attribution without a permanent dependency: enable sourcemaps for one throwaway build and run
`source-map-explorer` through `pnpm dlx`, which does not touch `package.json`. Revert the sourcemap
flag afterwards.

Then **write down a budget with a reason attached** — a number derived from install-time download on
a slow connection, not one carried over from public-web habits. If the analysis turns up something
genuinely large and genuinely unused, cut it; if it turns up React, the router and Dexie doing their
jobs, say so and move on. The point is to stop repeating an unmeasured claim, which is what H1 was.

### Commit 4 — the Actions workflow

Push to `main` → install with the frozen lockfile → typecheck → test → build → deploy → smoke check.
Requires the token in §3.

Two details specific to this repo:

- **The `minimum-release-age=10080` rule in `.npmrc` must not slow CI.** `--frozen-lockfile` installs
  exactly what the lockfile pins, so the age rule does not apply on install — but the workflow should
  pin `pnpm` to the `packageManager` field, because that rule was silently ignored by pnpm below
  10.16 and a floating CI pnpm could reintroduce the trap.
- **The token is `CLOUDFLARE_API_TOKEN` only.** No VAPID secret is needed until M8, and the D1
  database id is already in `wrangler.jsonc` and is not a secret.

### Commit 5 — correct the documentation

`infrastructure.md` currently estimates CPU at "~1–2 ms" and lists actual CPU as unverified. Both get
replaced by the measured figures, the sync-path number from commit 2, and a note on how to re-run the
query. The M2 and M3 plans get a correction line about H1, because a wrong remedy left in a plan is
worse than no remedy.

## 3. The one thing I need from you

**A Cloudflare API token, for GitHub Actions.**

Dashboard → My Profile → API Tokens → Create Token → *Edit Cloudflare Workers* template, or a custom
token with:

| Scope | Permission |
|---|---|
| Account → Workers Scripts | Edit |
| Account → D1 | Edit |
| Account → Account Settings | Read |
| User → User Details | Read |

It does **not** need R2, KV, Pages, DNS or Zone access. Narrower is better: this token can deploy
code, so it is the most powerful credential in the project.

Put it straight into the repository's secrets as `CLOUDFLARE_API_TOKEN` rather than pasting it to me
— GitHub → Settings → Secrets and variables → Actions. I can create the workflow that reads it
without ever seeing its value, which is how it should be.

## 4. Your ten-minute phone checklist

None of this can be verified with `curl`, and it is the half of M4 that actually answers whether the
app is any good.

1. **Install it.** Open the URL in Chrome on Android, menu → *Add to Home Screen*. Confirm the icon
   is the chevron mark and not a screenshot of the page.
2. **Open it from the Home Screen.** It should launch with no browser chrome, dark, portrait.
3. **Airplane mode, then log a session.** This is the real test and the whole point of the
   architecture — start a gate, log several sets, use the rest timer, finish. Everything must work
   with the radio off.
4. **The rest timer with the screen off.** Start a 210-second squat rest, lock the phone, wait a
   minute, unlock. The remaining time must be *correct*, not frozen — that is what M3's G6 fix was
   for, and a real device is the only place it can be checked.
5. **Lighthouse**, from desktop Chrome DevTools against the live URL, Progressive Web App category.
6. **Tomorrow morning:** confirm the Rest Day window, since tomorrow is Sunday.

Tell me what breaks. Everything on that list is a thing I cannot see.
